# General Mini Agent Framework 核心 Agent 项目范围设计

## 1. 项目目标

General Mini Agent Framework 将演进为面向外部 Python 开发者的通用开源 Agent 框架。

首要价值是提供一个轻量、清晰、可组合的单 Agent 工具调用内核，能够嵌入既有 Python 应用。框架不以功能数量为竞争点，而以稳定的执行语义、可隔离的实例状态和易测试的公共接口为基础。

首个稳定版本面向使用本地 Python 业务函数和 OpenAI 兼容模型服务构建工具调用型 Agent 的开发者。

## 2. 产品定位

框架是一个库，而不是托管平台、完整应用脚手架或工作流产品。开发者应能以少量 Python 代码完成以下闭环：

```text
业务函数 -> Tool Schema -> 模型工具调用 -> Agent 执行 -> 工具结果回写 -> 结构化轨迹
```

首个发布版本为 `0.1.0`，支持 Python 3.12。模型服务首版正式支持 OpenAI Chat Completions 兼容接口；接口设计保留最小模型协议，以便未来增加适配器，但不在 `0.1.0` 同时维护多个厂商实现。

## 3. 0.1.0 范围

### 纳入核心

- OpenAI 兼容模型客户端，含可配置超时和不泄露密钥的错误上下文。
- 基于 Python 函数签名生成 JSON Schema 的工具定义与执行机制。
- 单 Agent 同步 ReAct 执行循环，支持工具调用、工具结果回写和最大迭代上限。
- Agent 实例级工具注册表和会话状态，实例之间不得共享工具、上下文或运行轨迹。
- 结构化运行轨迹及结果数据，用于检查模型响应、工具调用、观察结果和结束原因。
- 带类型注解的稳定公共 API、最小可运行示例、离线单元测试、可复现安装和 CI。

### 不纳入核心

- 流式执行与流式事件协议。
- 短期记忆、长期记忆、向量数据库和持久化状态。
- 多 Agent、辩论、任务分发与工作流编排。
- 多厂商原生模型适配、复杂重试策略、权限系统和服务端托管能力。
- HTML 轨迹报告。它可保留为可选辅助模块，但不影响核心库的可用性。

现有不属于 `0.1.0` 范围的模块应被视为实验性或后续扩展候选，不得作为稳定核心能力宣传。

## 4. 架构边界

```text
应用代码
  -> Agent
      -> ToolRegistry (每个 Agent 一份)
      -> ChatModel 协议
      -> Trace / AgentResult
```

- `Agent` 仅负责迭代控制、消息组装、模型调用协调、工具结果回写和轨迹记录。
- `ToolRegistry` 负责工具 Schema、名称查找、参数校验和执行；不使用进程全局可变注册表。
- `ChatModel` 是最小模型调用协议；OpenAI 兼容 HTTP 客户端是其首个实现。模型客户端不执行工具，也不持有 Agent 业务状态。
- `Trace` 与 `AgentResult` 是结构化数据载体。渲染、持久化与观测后端必须位于核心执行路径之外。

稳定的公共 API 仅覆盖 `Agent`、`Tool` 或工具装饰器、`ChatModel`、配置类型、`AgentResult` 与 `Trace`。扩展只能通过最小模型协议、工具协议和结构化事件边界接入，不能要求核心依赖记忆、编排或存储实现。

## 5. 执行与错误语义

每次运行遵循以下顺序：

1. Agent 根据输入、当前会话消息和本实例工具 Schema 请求模型。
2. 模型返回最终文本时，Agent 结束并写入最终轨迹事件。
3. 模型返回工具调用时，Agent 在本实例注册表中验证并执行工具，将结果和轨迹写回消息，再进入下一轮。
4. 到达最大迭代次数时，Agent 以可识别的结束原因结束。

以下情况必须具有明确、可定位且不泄露密钥的错误类型或结束信息：模型请求失败、未知工具、工具参数无效、工具执行失败和达到最大迭代次数。所有异常路径都应在结构化轨迹中留下对应事件。

## 6. 质量与发布标准

`0.1.0` 发布前必须满足：

- 可通过标准 Python 包安装流程安装并运行最小示例。
- 默认测试完全离线，使用可替代的假模型，不要求 API Key、网络或外部数据库。
- 测试覆盖最终文本返回、单个和多个连续工具调用、Agent 工具隔离、无效参数、未知工具、工具异常和最大迭代结束。
- CI 在每次变更上执行测试、Python 编译检查和静态检查。
- README 只说明已发布能力，并将实验性 API 明确标识为非稳定接口。
- 核心 API 的破坏性变更优先提供弃用路径；扩展模块可在 `0.x` 阶段独立演进。

## 7. 分阶段扩展

后续能力按独立领域逐个进入，不将多个能力域捆绑发布：

1. `0.1`：单 Agent 工具调用核心。
2. `0.2`：流式执行。
3. `0.3`：可插拔短期和长期记忆。
4. `0.4`：多 Agent 协作。
5. 后续版本：工作流编排和可观测性增强。

每个阶段只有在实现、离线测试、示例和文档完整后才进入下一阶段。新能力必须证明不会破坏核心 API、实例隔离和离线可测试性。

## 8. 非目标

本项目近期不追求与大型 Agent 平台在集成数量或功能广度上竞争，也不承诺生产级分布式执行、复杂权限治理、服务端多租户或通用工作流 DSL。任何新需求均先判断是否强化单 Agent 工具调用内核；若否，则应作为可选扩展或独立项目评估。
