# General Mini Agent Framework 0.4.1 发布工程设计

## 状态

已于 2026-07-27 确认进入实施规划。

## 目标

`0.4.1` 将现有 `0.4.0` 功能基线收口为可复现、可检查、可人工发布的 Python
发行包。该版本不增加 Agent 运行时能力，而是确保最低支持版本与当前开发版本均能通过
离线验证，源码分发包和 wheel 可以构建、检查并在干净环境安装，同时为后续版本建立中文
变更记录和可复用的发布流程。

## 范围

`0.4.1` 包含：

- 在 Python 3.12 和 3.14 上运行现有离线测试；
- 将 lint、字节码编译和发行包验证从版本矩阵中分离，避免重复执行；
- 构建 sdist 和 wheel，并检查发行包元数据；
- 在干净虚拟环境安装 wheel，导入少量稳定公共 API 并核对安装版本；
- 统一仓库文档中的测试命令为 `python -m pytest tests -v`；
- 新增中文 `CHANGELOG.md` 和 `docs/RELEASING.md`；
- 将项目版本提升到 `0.4.1`，并同步 README、PLAN 和发布契约测试。

该版本不包含 PyPI 自动发布、GitHub Release 自动创建、包签名、制品证明、运行时新功能、
异步接口、工具执行控制或顶层 `core` 包迁移。

## 方案选择

采用两个职责分离的 CI job：

1. 兼容性测试 job 使用 Python 3.12 和 3.14 矩阵，只安装开发依赖并运行现有测试。
2. 发行验证 job 固定使用 Python 3.12，只执行 lint、字节码编译、sdist/wheel 构建、
   元数据检查和 wheel 干净安装冒烟。

没有选择在每个 Python 版本上重复构建发行包，因为构建产物是平台无关的纯 Python wheel，
重复执行不会提供与成本相称的额外信号。也不新增自定义发布脚本；当前步骤足够短，直接保留
为标准 Python 命令更容易审查和手工复现。

## 模块边界

`core/` 的实现和公共导出在 `0.4.1` 中保持不变。发行工程不得借机调整 Agent、模型、工具、
记忆、Debate 或 trace 的运行语义。

`.github/workflows/ci.yml` 负责编排自动验证，但不持有发布凭据，也不执行外部发布。
`pyproject.toml` 继续作为包名、版本、Python 要求、构建后端和可选依赖的唯一机器可读来源。
`CHANGELOG.md` 记录用户可见的版本变化；`docs/RELEASING.md` 记录维护者执行验证、合并、打 tag
和检查制品的步骤。README 和 PLAN 只描述当前真实能力，不把发布准备描述为运行时功能。

## 依赖与发行工具

运行时依赖保持为 `httpx`，Demo 和长期记忆可选依赖保持不变。新增独立的 `release` 可选依赖，
包含构建和元数据检查所需的 `build` 与 `twine`。这些工具不得进入默认运行时依赖。

本地发行准备使用：

```powershell
python -m pip install ".[dev,release]"
python -m build
python -m twine check dist/*
```

构建仍使用现有 Hatchling 后端。`0.4.1` 不更换构建系统，不引入锁文件，也不承诺所有开发工具
的逐字节可复现安装；本版本的“可复现”指从干净 Python 环境按声明依赖可以得到可安装且通过
验证的发行包。

## CI 数据流

代码推送或 Pull Request 触发 CI 后：

1. `test` job 分别创建 Python 3.12 和 3.14 环境。
2. 每个环境安装 `.[dev]`，运行一次完整的现有离线测试集。
3. `distribution` job 在 Python 3.12 安装 `.[dev,release]`。
4. 该 job 运行 Ruff 和 `compileall`，然后清理预期构建输出并生成 sdist/wheel。
5. `twine check` 检查两个制品的元数据和 README 渲染兼容性。
6. job 创建新的临时虚拟环境，通过 wheel 安装项目。
7. 临时环境导入 `Agent`、`Debate`、`LLM` 和 `MemoryQuery`，并使用
   `importlib.metadata.version()` 确认安装版本为 `0.4.1`。

发行验证只消费本次构建生成的 wheel。它不从工作区直接导入 `core`，从而能发现 wheel 漏包、
版本不一致和安装依赖缺失。

## 测试策略

保留现有 169 项测试，不删除或合并既有回归保护。`0.4.1` 不为 CI YAML、标准构建工具或
虚拟环境命令增加逐步骤单元测试。

自动化测试改动限制为：

- 修改现有包版本契约断言，使其要求 `0.4.1`；
- 在现有文档契约测试中检查 CHANGELOG、发布手册和统一验证命令的关键事实；
- 使用一个 CI 发行冒烟流程验证真实构建产物，不在安装后的 wheel 环境重复运行完整测试集。

每个实施任务只运行与改动直接相关的检查，最终发布任务只运行一次完整本地验证。Python 3.12
与 3.14 的跨版本结论以 CI 矩阵为准。

## 文档结构

`CHANGELOG.md` 使用中文 Keep a Changelog 风格，至少包含 `0.4.1` 和 `0.4.0` 两个版本条目，
按“新增、变更、修复”中实际存在的类别组织，不为凑格式创建空章节。

`docs/RELEASING.md` 是版本无关的维护者手册，包含：

- 发布前工作区、分支和版本检查；
- 离线测试、lint、编译和发行包验证命令；
- sdist/wheel 内容与元数据检查；
- 合并 `dev` 到 `main`、创建带 `v` 前缀 tag 的人工步骤；
- CI 失败时不得打 tag、tag 后发现问题时不得覆盖原 tag 的约束。

`README.md` 保留面向使用者的安装和验证入口，只链接 CHANGELOG 与发布手册，不复制整套维护者
流程。`PLAN.md` 的稳定版本边界更新为 `0.4.1`，但核心架构能力仍与 `0.4.0` 相同。

## 兼容性与已知风险

`0.4.1` 保持所有现有 Python 公共导入和行为。顶层包仍名为 `core`。当前环境已证明直接调用
`pytest` 可能优先导入 site-packages 中的同名包，因此仓库统一使用 `python -m pytest`，发行
冒烟则必须在干净虚拟环境运行。

重命名 `core` 会破坏公共 API，不属于补丁版本。该风险记录在发布手册的故障排查部分，后续如
需迁移，应单独设计兼容命名空间和弃用周期。

## 错误处理与发布边界

任何一个支持版本测试失败、lint 或编译失败、构建失败、`twine check` 失败、wheel 安装失败、
稳定 API 导入失败或版本核对失败，都应使 CI 失败并阻止人工打 tag。

CI 不自动修复元数据、不覆盖已有制品、不提交生成的 `dist/`，也不持有 PyPI token。发布人员
不得为通过检查而跳过失败步骤。已经推送的错误 tag 不得强制覆盖，应修复后提升补丁版本。

## 实施与提交边界

实施按以下可独立审查的边界组织：

1. 设计与实施计划文档；
2. 双版本 CI 与发行包冒烟验证；
3. 中文 CHANGELOG、发布手册和统一命令；
4. `0.4.1` 版本元数据、稳定文档与最终验证。

每个边界形成一个小提交。生成的 sdist、wheel、临时虚拟环境和缓存均不得提交。

## 验收标准

`0.4.1` 在满足以下条件后可以合并并人工打 tag：

- Python 3.12 和 3.14 的现有离线测试全部通过；
- Ruff、`compileall` 和 `git diff --check` 通过；
- 一次构建同时生成版本为 `0.4.1` 的 sdist 和纯 Python wheel；
- `twine check` 对全部发行制品通过；
- 干净虚拟环境能从 wheel 安装项目、导入选定稳定 API 并读到版本 `0.4.1`；
- 中文 CHANGELOG、发布手册、README、PLAN 和 ROADMAP 与真实能力一致；
- `core/` 运行时行为与稳定公共 API 未发生变化；
- CI 不包含任何外部发布凭据或自动发布动作。
