# General Mini Agent Framework 0.3.1 Long-Term Memory Design

## Status

Approved for implementation on 2026-07-27.

## Goal

Add explicit, persistent, namespaced long-term memory without making Agent runs perform hidden
retrieval or hidden writes. The feature must remain provider-neutral, preserve the stable `0.3.0`
context budget, and isolate users, conversations, and Agents by default.

## Scope

`0.3.1` stabilizes:

- structured long-term memory records and queries;
- three-part namespaces and explicit retrieval scopes;
- a replaceable long-term memory store protocol;
- a deterministic in-memory store for offline use and tests;
- a lazily loaded ChromaDB persistent adapter;
- exact metadata filtering across supported backends;
- optional, explicit Agent retrieval on synchronous and streaming runs;
- bounded memory context injection and a visible `memory_error` terminal state.

The release does not add automatic memory selection, automatic writes, web search, async storage,
complex metadata expressions, score normalization, reranking models, or online tests.

## Module Boundary

Create `core/long_term_memory.py` for the stable contracts and implementations. Keep
`InMemoryConversation` in `core/memory.py`: conversation history and persistent semantic memory are
different responsibilities. The existing experimental `LongTermMemory` remains a compatibility
export for `0.3.1` but is not used by the stable Agent integration.

The Agent coordinates an explicitly requested query. The store owns indexing and Embedding. The
context policy retains final authority over the complete request sent to the model.

## Data Contracts

`MemoryNamespace` is a frozen dataclass containing non-empty `user_id`, `conversation_id`, and
`agent_id` strings.

`MemoryScope` supports:

- `exact`: match all three namespace fields;
- `user_agent`: match `user_id` and `agent_id` across conversations;
- `user`: match `user_id` across conversations and Agents.

`MemoryRecord` contains `id`, `content`, `namespace`, `metadata`, `created_at`, and `updated_at`.
IDs use UUID strings and timestamps are timezone-aware UTC datetimes generated by core helpers.
Record content must be non-empty text. Metadata keys must be non-empty strings and may not use
reserved namespace keys.

`MemoryQuery` contains query text, namespace, scope, `top_k`, exact `metadata_filter`, and
`max_context_tokens`. Query text is non-empty; `top_k` and the memory context budget are positive.
The default scope is `exact`.

## Store Protocol

`LongTermMemoryStore` defines:

```python
def store(content, namespace, metadata=None) -> MemoryRecord: ...
def get(record_id, namespace) -> MemoryRecord | None: ...
def query(query: MemoryQuery) -> list[MemoryRecord]: ...
def update(record_id, namespace, *, content=None, metadata=None) -> MemoryRecord: ...
def delete(record_id, namespace) -> bool: ...
def clear(namespace, *, scope="exact") -> int: ...
```

Every `store()` creates a new record. Duplicate content is allowed. `update()` and `delete()` require
both an ID and the exact owning namespace, preventing a broad scope from mutating another record.
Updates retain `id` and `created_at` and replace only explicitly supplied fields. Missing records
raise `MemoryRecordNotFound` for update and return `False` for delete.

Queries return at most `top_k` records in descending relevance order. The stable contract does not
expose a normalized score. A backend may retain its raw score in private diagnostics, but callers
must not compare scores across backends.

Store failures use `MemoryStoreError` with safe operation and backend context. Errors must not
contain record text, query text, credentials, or raw remote response bodies.

## In-Memory Store

`InMemoryLongTermStore` keeps defensive record copies in one instance. It implements deterministic
offline ranking using case-insensitive term overlap, with creation order as a tie breaker. This is a
test and local-development backend, not a claim of semantic-vector equivalence.

Namespace scope and metadata filtering occur before ranking. `get`, `update`, `delete`, and `clear`
require exact ownership or an explicit clear scope. Separate instances share no records.

## ChromaDB Adapter

`ChromaMemoryStore` accepts `persist_dir` and `collection_name`. It imports ChromaDB only on first
operation and uses `PersistentClient`. ChromaDB owns document Embedding and vector indexing.

Namespace fields and user metadata are stored as flat Chroma metadata. Reserved internal keys cannot
be supplied by callers. Scope and exact metadata filters are translated to Chroma's conjunction
filter. Results are converted back to `MemoryRecord` in the order returned by Chroma.

The adapter wraps initialization and operation failures as sanitized `MemoryStoreError`. Tests use
small fakes and missing-dependency simulation; they do not test ChromaDB's own ranking algorithm.

## Agent Integration

`Agent` gains optional `long_term_memory: LongTermMemoryStore | None`. Both run methods gain a
keyword-only `memory_query: MemoryQuery | None`:

```python
agent.run(user_input, memory_query=query)
agent.run_stream(user_input, memory_query=query)
```

No query means no long-term memory operation. Supplying a query without a configured store produces
`memory_error`. The Agent never calls `store()` automatically.

When requested, retrieval occurs once at the start of the run before any model request. A store
failure returns `memory_error` without contacting the model or changing conversation memory. An empty
successful result continues normally without a memory block.

Retrieved records are formatted in relevance order as one system reference block after the primary
system prompt. The block states that retrieved text is historical data, not system instructions.
Whole records are appended until `max_context_tokens` is reached; record content is never sliced.
Oversized records are skipped. If records exist but none fit, the run returns
`context_budget_exceeded` before model access.

The memory sub-budget uses `ApproximateTokenCounter`. The resulting complete message list still passes
through the configured `ContextPolicy` before every model request, so the main context budget remains
authoritative. Retrieved memory is request-local and is never written into `InMemoryConversation`.

## Terminal Behavior

Add `memory_error` to `AgentStopReason`. The synchronous path returns `AgentResult`; the streaming
path emits its normal `iteration_start` followed by one `done(memory_error)`. No new stream event type
is required. Trace records a sanitized `memory_error` entry.

Successful sync and fully consumed streaming runs retain the `0.3.0` writeback contract: only the
original user input and final assistant answer are appended to conversation memory.

## Minimal Testing Strategy

Add approximately 12-15 focused tests, using parameterization where behavior is shared:

- contract validation and namespace scope matching;
- in-memory isolation, exact metadata filtering, ranking, update, and delete;
- ChromaDB lazy loading and translation through a small fake;
- explicit Agent retrieval, bounded injection, no automatic writes, and `memory_error`;
- one sync and one stream integration path where behavior genuinely differs;
- stable exports, version, Demo, and documentation contracts.

Each implementation task runs only its focused tests. Full verification runs once during release:

```bash
python -m pytest tests -v
python -m compileall -q core demo tests
ruff check core tests demo
git diff --check
```

## Documentation and Release

- export stable long-term memory contracts and adapters from `core`;
- add an offline/persistent long-term memory Demo without web search;
- document namespace safety, explicit retrieval, explicit writes, and approximate memory budgeting;
- update `PLAN.md` and remove completed `0.3.1` items from `ROADMAP.md`;
- bump package version to `0.3.1` only after final verification passes.

## Acceptance Criteria

`0.3.1` is ready when records cannot cross namespace boundaries by default, explicit broader reads
work only at the requested scope, metadata filters behave the same across stores, Chroma remains an
optional delayed dependency, Agent retrieval is opt-in and budgeted, retrieval failures are visible
before model access, no Agent path writes long-term memory automatically, existing `0.3.0` behavior
remains compatible, and all final verification commands pass.
